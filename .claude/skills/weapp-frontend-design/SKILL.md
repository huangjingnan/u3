# 微信小程序产品方案设计

把学员一句模糊的产品想法，拆成一份**易读**的方案。学员确认后，**自动交接**给 `weapp-dev-workflow` 进入开发。

> **本 Skill 的边界（重要）**
> - ✅ 写产品：核心功能、页面清单、字段名、Mock 数据规模、不做的事
> - ❌ **不写**技术约束：Mock 写法、状态栏高度、安全区、自测要求等 → 这些都在 `weapp-dev-workflow` 里
> - ❌ **不写**代码：CSS / JS / API 调用一律不出现
> - 学员确认后，**主动调用** `weapp-dev-workflow`（不是依赖、是 handoff）

**调用方式**：在 Cursor / Claude Code / Codex 中对 Agent 说

> "用 weapp-frontend-design 帮我设计一个【xxx】小程序"
>
> 或
>
> "我想做一个【xxx】小程序，先帮我设计一下"

---

## 1. 四步流程

```
Step 1  需求澄清（最多 3 轮，每轮只问 1 题）
   ↓
Step 2  出产品方案（按 §3 模板，写入 docs/prd/<feature>.md）
   ↓
Step 3  用户确认门（学员可增删改，AI 跟着改到满意）
   ↓
Step 4  交接（明确告诉学员"现在交给 weapp-dev-workflow 开发"）
```

### Step 1 · 需求澄清

**触发条件**：学员输入很短 / 含"大概 / 类似的 / 想要个"等模糊词 / 没说清是给谁用 / 没提关键交互。

**规则**：
- 一次**只问 1 个**最关键的问题（最影响范围的优先）
- 最多问 **3 轮**，超过 3 轮还没收敛 → 用合理默认值继续
- 给出 3~5 个**带语义标签的选项**（不是开放问题）
- 学员答完上一题再问下一题

**第 1 题通常问**（按优先级选一个）：
1. **给谁用 / 规模**（自己 / 少数人 / 多人协作）—— 决定要不要"多账本 / 成员"等最大模块
2. **核心动作是什么**（浏览 / 预约 / 录入 / 交易）—— 决定核心页面数量
3. **要后端吗**（要 / 不要）—— 本 Skill 强制"不要"，但要确认学员没误解

### Step 2 · 出产品方案

**按 §3 模板**生成完整方案，**必须**写入 `docs/prd/<feature>.md`（feature 用中文名或英文 slug，例如 `docs/prd/汽车保养预约.md`）。

写完后**同时**在对话里完整呈现给学员。

### Step 3 · 用户确认门

方案呈现后**必须**收尾三选一：

```
⏸️ 请确认：
- 回复「确认」→ 我立即交接给 weapp-dev-workflow 开始开发
- 回复修改意见（如「增加优惠券模块」「去掉美容分类」）→ 我更新方案，再来确认
- 觉得整体方向不对 → 告诉我哪里要重新设计
```

**铁律**：
- 🚫 **没拿到学员明确「确认」之前不交接**
- 学员提任何修改 → 改方案 → 版本号 `v0.1` → `v0.2` → `v0.3` ……→ **再次**确认门
- 不限制修改轮次，直到学员说「确认」

### Step 4 · 交接

学员说「确认」后，输出交接播报：

```
✅ 方案已确认。

📄 PRD 文件：docs/prd/<feature>.md
🚀 下一步：现在交给 weapp-dev-workflow 在其内部约束下开始开发
   （Mock 数据 / 自测 / 安全区 / 机型覆盖等约束都在 weapp-dev-workflow 里负责）

Agent 现在切换到 weapp-dev-workflow，按 docs/prd/<feature>.md 的核心功能清单实现。
```

**交接 ≠ 强制门**：
- `weapp-dev-workflow` 仍然**可以独立调用**（学员直接说"开发一个【xxx】小程序"也 OK）
- 学员不跑本 Skill，**不会**少任何能力、**不会**报错
- 三个 Skill 是**正交独立**的，本 Skill 是"先想清楚再动手"的可选工具

---

## 2. 易读颗粒度（强制标准）

PRD 的**详细程度**锁在这一层，**不多不少**：

### ✅ 写到这一层
- `pages/路由名` 级别（如 `pages/order/create`）
- 每个页面：可见模块 + 关键元素 + 关键文案 + 关键字段名
  - 例：「车牌号（下拉选省份 + 输入字母数字）」
  - 例：「状态：待到店 / 已完成 / 已取消」
- Mock 数据文件位置 + 种子规模
  - 例：`my-app/src/utils/mock.js`，≥2 家门店、≥8 个服务项目
- 不做的事（用 `🚫` 列出）

### ❌ 不写到这一层
- 字段类型 / TS 接口 / 函数签名
- 任何代码示例（CSS / JS / API 调用）
- "状态栏动态获取""安全区适配""机型覆盖"等 → 留给 `weapp-dev-workflow`
- 任何后端 / 鉴权 / 云 / API 语义

## 4. 标准范例：汽车保养预约小程序

> 学员原话："我想做一个汽车保养预约小程序。"
> 这份是**本 Skill 产出的标准形态示例**——可读、清楚、不越界。

```markdown
# 产品方案：汽车保养预约小程序

> 纯前端实现 · 所有数据走 Mock · 适用于 unibest 微信小程序脚手架

## 一、一句话需求
帮车主在线预约附近门店的汽车保养服务，支持浏览服务项目、提交预约单、查看历史订单。

## 二、用户是谁
- 车主（唯一用户角色）
- 没登录也能用（首次打开用昵称 + 头像占位即可）
- 一个人用，不需要多人协作

## 三、典型使用流程
打开小程序 → 看到门店和保养项目 → 选一个项目进详情
→ 选到店时间 + 填车牌/车型/电话 → 提交预约单
→ 看到「预约成功」页面 → 之后从「我的」里查订单

## 四、核心功能
1. **首页（pages/index）**
   - 顶部 Banner：门店介绍（地址、营业时间、联系电话）
   - 中部快捷入口：「立即预约保养」
   - 底部服务分类入口：保养 / 维修 / 美容 / 检测

2. **服务列表（pages/services）**
   - 按分类展示保养项目（小保养、大保养、换胎、电瓶检测等）
   - 每个项目展示：名称、首图、价格、标签（如"热门"）

3. **服务详情（pages/services/detail）**
   - 大图 + 项目说明（文字 2~3 段）
   - 价格、预计耗时、包含项（列表）
   - 底部固定按钮：「立即预约」

4. **预约下单（pages/order/create）**
   - 选择到店日期 / 时段（至少展示未来 7 天 × 每 2 小时一段）
   - 填写车辆信息：车牌号（下拉选省份 + 输入字母数字）、车型（自由输入）
   - 填写联系人：姓名、手机号
   - 底部固定按钮：「提交预约单」（带安全区适配）

5. **订单列表（pages/order/list）**
   - 时间倒序展示所有预约单
   - 每条显示：服务名、门店、到店时间、状态（待到店 / 已完成 / 已取消）
   - 点击进订单详情（pages/order/detail）：完整字段 + 取消按钮

6. **个人中心（pages/mine）**
   - 头像 + 昵称
   - 入口：「我的预约」→ 跳订单列表
   - 入口：「联系门店」「关于我们」

## 五、Mock 数据约定
- **文件位置**：`my-app/src/utils/mock.js`（unibest 约定，相对本仓库根的 `my-app/` 子目录）
- **种子数据规模**：
  - 门店：≥ 2 家（覆盖"附近门店"概念）
  - 服务项目：≥ 8 个（保养 / 维修 / 美容 / 检测 各 ≥ 2）
  - 预约时段：未来 7 天 × 8 段/天
  - 历史订单：≥ 3 条（不同状态各 1 条）

## 六、关键页面交互

| 页面 | 关键交互 |
|------|----------|
| 首页 | 顶部状态栏动态高度；Banner 点击拨打电话 |
| 列表 | 下拉刷新 / 上滑加载更多（Mock 分页，每页 5 条） |
| 详情 | 大图懒加载；"立即预约"按钮固定底部 |
| 下单 | 车牌号分段输入；时段单选；表单未填完禁用提交按钮 |
| 订单列表 | 状态用 tag 颜色区分（蓝=待到店 / 灰=已完成 / 红=已取消） |
| 个人中心 | 头像圆形，点击无操作（Mock） |

## 七、非功能性约束（来自 weapp-dev-workflow）
- 状态栏高度（动态获取）
- 底部安全区适配
- 机型覆盖自测

## 八、边界 / 不做的事
- 🚫 不做登录、不做鉴权、不做支付
- 🚫 不做真实定位（门店距离用 Mock 数字）
- 🚫 不做后端 API、不接云函数、不上云
- 🚫 不做商家端 / 技师端 / 配送端
- 🚫 不做消息推送
```

---

## 5. 不要做的事

- 🚫 **不要**在 PRD 里写代码、字段类型、API 签名 → 留给 `weapp-dev-workflow`
- 🚫 **不要**绕开确认门直接进入开发 → 没拿到学员「确认」就交接是 P0 错误
- 🚫 **不要**一次甩 10 个问题给学员 → 1 轮 1 题，最多 3 轮
- 🚫 **不要**写"可选 / 待定"章节 → 任何不确定项要么确认、要么给默认值
- 🚫 **不要**在 PRD 里写"技术架构 / 部署方案 / 安全方案" → 越界
- 🚫 **不要**省略"不做的事"章节 → 显式列出能避免后续无效追问
- 🚫 **不要**修改用户没提的功能 → 用户没说要"收藏 / 评分"，别自作主张加
